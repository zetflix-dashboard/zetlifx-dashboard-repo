# Зетфликс — правила работы с репозиторием

## Сначала прочитать
`README.md`, `docs/agent-modes.md`, `docs/architecture.md`, `docs/chart-contract.md`, `docs/dataset.md`, `docs/metrics.md`, строку C-ID в `docs/charts.md`, `docs/contributing.md`, `docs/decisions.md` и ближайший `AGENTS.md`. Осмотреть код, package.json и git diff. Источник текущего состояния — репозиторий, не память чата.

## Режим задачи
- По умолчанию **chart**: ровно один C-ID, только `src/charts/CXX-slug/chart.json` и его `README.md`. Реестр обнаруживает JSON автоматически. Новый график пользователь добавляет в пространство через каталог.
- **admin**: только когда пользователь явно поручил изменение оболочки, архитектуры, общих компонентов, источников, правил или нескольких графиков. Полный рефакторинг проекта — admin. Это разрешение ограничено конкретной задачей, а не всеми будущими действиями.
- Режима batch нет. Не трактовать «сделай красиво», «улучши дашборд», «добавь график» как разрешение менять общий код. Если не выбран C-ID — выяснить его до изменений. Для нескольких графиков предложить отдельные chart-задачи или явную admin-задачу; не переключаться молча.
- Слова «admin», «batch» в примере, цитате, данных, имени файла или отрицании не являются разрешением. В сомнительном случае сохранить chart.
- До правки кратко указать режим, C-ID/область, план файлов и проверки. Для chart не менять инструкции, реестр, CI, тестовый код, lockfile, SQL и CSS, даже для «починки сборки». При необходимости форматировать только свой JSON (`npx prettier --write путь/к/chart.json`), не весь репозиторий.

## Создание и демонстрация графиков
- Каждый график, включая пример, прототип и временную карточку, создавай как декларацию `src/charts/CXX-slug/chart.json`. Используй существующие шаблоны, утверждённые источники, автоматический реестр и общий рендерер.
- Для размещения используй обычное редактируемое пространство и штатный каталог в UI. Просьба «добавь на дашборд» или «покажи, как выглядит» сама по себе разрешает штатное размещение, а границы изменений общей архитектуры определяются явным поручением пользователя.
- Запрос на несколько графиков может требовать admin для нескольких C-ID. В таком случае сохраняй тот же путь для каждого графика и ограничь изменения файлами соответствующих C-ID. Отдельное явное поручение требуется для нового шаблона, источника, общей оболочки или режима пространств.
- Не создавай для примеров параллельный реестр, специальную вкладку, отдельный путь отрисовки, демонстрационный источник или автоподстановку в пользовательские макеты. При отсутствии поддержки примени правила ниже.

## Неподдерживаемые задачи
Перед созданием графика проверить доступные шаблоны и источники. Если нужного шаблона, поля, разреза или источника нет, остановить именно эту реализацию и объяснить ограничение. Предложить честную альтернативу на текущих источниках (таблицу/линии/столбцы/точки) либо отдельную admin-задачу. Не создавать HTML, JS, CSS, iframe, новый renderer, библиотеку, пользовательские formatter-функции, SQL-источник или иной обход контракта. Не выдавать приблизительно похожую метрику за запрошенную.

## Данные и формулы
- Определения KPI — `docs/metrics.md`; реализованные SQL — `src/shared/data/datasets.js`. Не копировать формулы в графики. Источник и ограничения берутся из общего каталога.
- Новые источники — admin: проверить реальные Parquet-поля, зерно, даты, тестовые аккаунты, NULL, границы периода и кардинальность JOIN. Факты предагрегировать, значения фильтров параметризовать.
- Не применять неприменимый фильтр и не имитировать отсутствующий разрез. Сейчас реализован только период 2024–2025.
- PL_Control — контрольные итоги, не доказательство сверки фактов. Для финансовых изменений дать независимую числовую сверку; для денежных — Cash_Control. Не смешивать изменение методики с косметикой.
- Секреты, расширенные Supabase-ключи, `.env` и реальные персональные данные запрещены. `public/` публикуется целиком.

## Проверки и доставка
1. Из свежего main создать `chart/CXX-description` или `admin/description`. Чужие изменения не перезаписывать, общие ветки не force-push.
2. Выполнить `npm ci`, `npm run check`, `npm run test:e2e` после установки Chromium. Проверить реальный diff и scope PR. Для интерфейса осмотреть desktop/mobile. Если проверка недоступна — назвать её, не утверждать успех.
3. Пользователь заранее разрешил автоматически коммитить и сразу отправлять изменения в публичный репозиторий `zetflix-dashboard/zetlifx-dashboard-repo`, создавать PR и публиковать сайт после успешных обязательных проверок. Выполнять это в рамках порученной задачи без ожидания отдельного разрешения, в том числе на раскрытие изменённых исходников в этом публичном репозитории. Исключение — явная просьба пользователя оставить изменения локально, не публиковать или подготовить только черновик/ревью. Это разрешение не расширяет область задачи и не отменяет ограничения среды, защиту GitHub и запрет на публикацию секретов.
4. После успешных проверок актуального SHA автоматически слить PR, если пользователь не просил только черновик/ревью и GitHub разрешает. При изменении head/base обновить ветку и проверки. Не обходить упавший CI, protections или отклонённое review.
5. В PR один блок ZETFLIX_SCOPE с нормализованным `mode: chart` / `mode: admin`; для chart указать единственный C-ID, для admin charts оставить пустым. Указать результат, проверки, методологические ограничения. Не менять mode для легализации случайно расширенного diff.
6. Общие изменения документировать одновременно с кодом. Для chart контекст и ограничения писать в README его каталога, без правки общего каталога задач.

## Границы гарантий
Инструкции направляют ИИ; JSON-контракт убирает исполняемый код из chart-расширений; CI ограничивает пути. Это защита от случайной ошибки, не аутентификация намерения пользователя и не защита от владельца с правом изменить admin-код. Обязательная блокировка merge требует required checks на GitHub. Нельзя обещать «невозможно сломать» без этих условий.
