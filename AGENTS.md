# Зетфликс — обязательные инструкции Codex

**ПЕРВОЕ ПРАВИЛО: режим CHART по умолчанию.** Прежде чем что-либо менять, прочти `docs/agent-modes.md` и вслух укажи режим и конкретный C-ID. Без явного согласия пользователя **никогда** не расширяй изменения до оболочки или второго графика. Слова `BATCH`, `Batch`, `batch`, «режим батч» означают одно намерение; это не требует точного регистра.

## Перед разработкой
1. Прочти `README.md`, `docs/agent-modes.md`, `docs/charts.md`, `docs/metrics.md`, `docs/dataset.md`, `docs/architecture.md`, `docs/dashboard-editor.md`, `docs/contributing.md`, `docs/decisions.md`, `src/charts/AGENTS.md` (если работаешь с графиками).
2. Изучи физические поля используемых Parquet, существующие модули `src/charts/C03-financial-trend/index.js` и `src/charts/C18-advertising/index.js`, действующий JS-контракт. Не предполагай несуществующие поля или функции.
3. Запиши: выбранный режим, C-ID, разрешённые пути, SQL-источники/зерно, применимые фильтры, план проверки. Если запрос неопределён («сделай всё красивее», «поправь графики») — уточни, не трогай файлы.

## Области записи
- **CHART:** создание, изменение и тесты **ровно одного** `src/charts/CXX-*/**`. Все другие файлы только для чтения. `src/charts/AGENTS.md` запрещено менять.
- **BATCH:** только при явном запросе и перечислении минимум 2 C-ID; разрешены лишь указанные директории `src/charts/CXX-*/**`. Не затрагивай движок.
- **ADMIN:** только при явно заявленном намерении изменить оболочку/архитектуру. Разрешено менять необходимые файлы, но минимально и с проверкой совместимости. Любой участник может сознательно запросить ADMIN; это не система аутентификации.
- Если для графика требуется новый компонент/серия ECharts, глобальный фильтр, реестр, макет, CSS оболочки, общий SQL или библиотека — **не меняй их в CHART/BATCH**. Сообщи, что требуется отдельная ADMIN-задача.
- Новый C-ID автоматически подхватывается `ChartRegistry` и добавляется в сетку механизмом AutoCharts; не редактируй `src/dashboards/overview.json` ради обычного графика.

## Методика и безопасность
- Истина: проверенная физическая Parquet-схема и оригинальная инструкция датасета → docs/metrics.md → реализация. При конфликте опиши расхождение, не угадывай.
- SQL параметризуй; не вставляй сырые значения фильтров. Не соединяй несколько фактов в одну строку без согласованного зерна и предварительной агрегации.
- Исключай тестовые аккаунты/события, не путай признание выручки с денежными поступлениями, учитывай годовые подписки/возвраты. Сверяй P&L с `pl_control`, денежные итоги с `cash_control` на одинаковой детализации.
- Не применяй фильтр к метрике без подтверждённого соответствующего измерения. Деньги — точные decimal, отсутствующий знаменатель — NULL.
- Не добавляй личные данные, токены, `.env`, секреты Supabase и новые публичные данные без явного ADMIN-задания.

## Как сдавать
- Ветка от актуального `main`: `chart/C04-...`, `batch/...` или `admin/...`. Один PR — один scope. Не пушь напрямую в `main`.
- PR имеет декларацию режима в описании по `docs/agent-modes.md`. Если CHART не указан, CI всё равно разрешает **только один** график; BATCH и ADMIN обязательно указываются явно.
- Запусти доступные тесты и сборку; не заявляй, что тесты прошли, если не запускались. Для финансовых графиков укажи числовую сверку.
- Изменения других графиков, движка и документов вне режима блокирует `Scope changes` GitHub Action. Не переключай режим задним числом ради успешного CI.
- Сообщай пользователю ссылки на PR, затронутые пути, проверенные команды и ограничения. Старые чаты не являются источником правил.
