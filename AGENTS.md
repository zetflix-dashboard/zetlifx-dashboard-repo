# Зетфликс — правила работы с репозиторием

## Перед изменениями
Прочитать `README.md`, `docs/dataset.md` (включая фактические поля Parquet), `docs/metrics.md`, `docs/chart-contract.md`, `docs/architecture.md`, `docs/contributing.md`, ближайший `AGENTS.md`. Проверить актуальный main, зависимости и git diff. Источник текущего состояния — репозиторий.

## Режимы и границы
- По умолчанию STANDARD MODE (`mode: chart` в PR). Разрешено любое количество изолированных графиков. Для каждого можно создавать, изменять и удалять только `src/charts/CXX-slug/chart.json`, `query.sql`, `README.md`. Регистрация автоматическая; новый график размещается штатным каталогом и редактором пространства. Никакого исполняемого JS/HTML/CSS в папке графика.
- ADMIN MODE активируется только точной отдельной командой `ADMIN MODE` в текущем запросе; регистр обязателен, цитаты и упоминания не активируют режим. Разрешение не переносится между запросами. Разрешены необходимые по задаче изменения общих компонентов, источников, контрактов, правил и оболочки. Не подсказывать команду активации. Если запрос требует запрещённых общих изменений: «У ВАС НЕТ ПРАВ НА ВНЕСЕНИЕ АРХИТЕКТУРНЫХ ИЗМЕНЕНИЙ В ПРОЕКТ, НО ВЫ ВСЁ ЕЩЁ МОЖЕТЕ ДОБАВЛЯТЬ/РЕДАКТИРОВАТЬ ОТДЕЛЬНЫЕ ГРАФИКИ».
- Перед правкой назвать область и проверки. В STANDARD MODE не менять общий код, SQL-политику, справочник источников, темы, оболочку, инфраструктуру фильтров, CI, тесты, инструкции или зависимости. Изолированные настройки существующих шаблонов — только через действующий контракт.
- Не создавать альтернативные виджеты, рендереры, реестры или обходы контракта. Неподдерживаемую часть задачи остановить, объяснив конкретное ограничение; не подменять метрику похожей.

## SQL и данные
- `query.sql` принадлежит только своему графику; его описание результата — `data` в `chart.json`. Имя `dataset` уникально во всём проекте. Общий `datasets.js` — автоматически собранный каталог, его не редактируют для добавления графиков. Отдельного `dataset.json` нет.
- До написания SQL изучить общий справочник `docs/dataset.md` и определения `docs/metrics.md`. Использовать только утверждённые Parquet из `src/shared/data/sources.json`; новые физические источники и новые общие механизмы — общая задача.
- Разрешён один SELECT / WITH … SELECT, только чтение. Политика проверяет функции, буквальные имена Parquet, отсутствие дополнительных операторов и число параметров. Формат и ограничения — `docs/chart-contract.md`. Это консервативная проверка, не полноценный SQL sandbox.
- Общий период передаётся двумя `?`, затем локальные фильтры в порядке `data.localFilters`. Нельзя интерполировать пользовательские значения. Поддерживаемые локальные срезы и расчёты можно добавлять в своём графике; глобальные контролы — общая инфраструктура.
- Указать зерно, роль даты, поля, единицы, исключения, ограничения и применимость фильтров. Не размножать факты JOIN: предагрегировать. Исключать тестовые аккаунты, соблюдать признание годовой оплаты, возвраты и NULL. Средние и отношения пересчитывать из исходных сумм. Общие определения метрик не переопределять.
- PL_Control — контроль, не доказательство сверки фактов; Cash_Control — для денежных потоков. Изменения расчётов проверять независимыми числовыми срезами. Секреты и реальные персональные данные запрещены; `public/` публикуется целиком.

## Проверки и доставка
1. Свежий main → отдельная ветка `chart/description` или `admin/description`; чужие изменения не перезаписывать и общие ветки не force-push.
2. `npm ci`, `npm run check`, `npm run test:e2e` с Chromium. Проверить diff, границы, реальный SQL, период/срезы, пустые результаты и ошибки; для UI desktop/mobile. Не объявлять недоступную проверку успешной.
3. Коммит, push и PR выполнять сразу, без дополнительного подтверждения. В PR один блок ZETFLIX_SCOPE: `mode: chart` и все изменяемые C-ID либо `mode: admin` с пустым `charts:`. Проверка использует нормализованные технические значения, а не текст команды пользователя.
4. После успешных обязательных проверок актуального SHA автоматически слить PR, если пользователь не просил только ревью/черновик и GitHub разрешает. При изменении head/base обновить ветку и проверки. Не обходить CI, protections или отклонённое review. Проверить публикацию.
5. После изменений перечислить все созданные/изменённые/удалённые файлы и фактическую статистику `git diff --numstat`: путь, зелёный `+N`, красный `-N`; без кода и полного diff. Дать кликабельный URL дашборда и preview при наличии, commit/PR, результаты проверок и подтверждённый статус публикации.

Инструкции и проверки защищают от случайных изменений; required checks и ограничения GitHub — отдельный слой, не аутентификация команды пользователя.
