# Как команде работать через ChatGPT / Codex

## Обычная задача участника
1. Выбрать свободный C-ID из `docs/charts.md`. Предварительно договориться, кто владеет графиком; не назначать нескольких авторов одного C-ID.
2. Открыть ChatGPT/Codex с подключенным GitHub, выбрать репозиторий `zetflix-dashboard/zetlifx-dashboard-repo`. Скопировать шаблон задания ниже. Агент должен прочитать `AGENTS.md` и документы, а не полагаться на память чата.
3. Начинать работу от последнего `main` в своей ветке. Один PR = один график или один логически связанный инфраструктурный блок. Не работать напрямую в main.
4. Codex готовит код и тесты, запускает доступные проверки, обновляет документацию, открывает PR. Участник проверяет цифры/фильтры/отображение и просит review. Любые формулы или общий код требуют особого внимания.
5. После merge обновить статус C-ID, закрыть задачу, удалить ветку. При конфликте с main — обновить ветку и заново проверить, не делать force-push чужих коммитов.

## Шаблон запроса к Codex
> Прочитай AGENTS.md и все документы, на которые он ссылается. Реализуй **CXX** по docs/charts.md. Сначала перечисли нужные таблицы, зерно, роль дат, определения мер, применимые и неприменимые фильтры, план файлов и проверок. Затем реализуй только свой модуль с использованием общего контракта и общего слоя SQL/фильтров. Проверь фактические Parquet-поля, контролируемые расчёты, ошибки, пустую выборку и работу на сайте. Не меняй другие графики и бизнес-правила. Работай в отдельной ветке, создай PR с тестами, контрольными числами и допущениями. Если отсутствует инфраструктура, предложи минимальный отдельный инфраструктурный PR, не делай скрытую несовместимую замену архитектуры.

## Конфликты и право менять общее
| Область | Кто меняет | Условие |
|---|---|---|
| `src/charts/CXX` | ответственный графика | обычный PR |
| `src/shared/**`, реестр графиков, фильтры | назначенный интегратор после review | отдельное объяснение совместимости |
| `docs/metrics.md`, `docs/dataset.md`, data | ответственный за методологию/данные после review | контрольная сверка и документирование |
| `AGENTS.md`, конфиги сборки и CI | ответственный за проект после review | обоснование и проверка всей сборки |

Имена ответственных пока **не назначены**. Не добавлять фиктивные GitHub usernames в CODEOWNERS. Администратор вручную включает required PR review, защиту main, проверки и, при необходимости, CODEOWNERS — Markdown-инструкция не изменяет GitHub permissions.

## Чек-лист PR
- [ ] Что сделал (ID, задача) и что не делал
- [ ] Изменённые файлы и общий API/контракт
- [ ] Источники, формулы, зерно, даты, исключения
- [ ] Поддерживаемые/неподдерживаемые фильтры
- [ ] Доказательство отсутствия двойного счёта
- [ ] Сверка чисел с PL_Control/Cash_Control (если применимо), величина дельты
- [ ] Реально запущенные команды тестирования; что не удалось проверить
- [ ] Снимок экрана для визуального PR после появления UI
- [ ] Известные ограничения/допущения, нужна ли миграция или обновление документации

## Командные договоренности
- Слияние PR — только после review; авто-мерджи не включать без CI.
- Не создавать по копии файла с общим SQL в каждой ветке; вносить независимые изменения в график, обсуждать общие контракты через PR.
- В задачах с отсутствующими файлами не притворяться, что приложение уже создано.
- Продолжение в новом чате: дать ссылку на PR / issue и поручить агенту прочесть файлы и изменения, а не пересказывать старую переписку.
- Никаких токенов и секретов в PR; публичные Parquet проверять отдельно.
