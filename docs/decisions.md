# Реестр архитектурных решений и открытых вопросов

## Исторические решения MVP (статусы заменены ADR-005–007)
- ADR-001 (план): модульная frontend-архитектура, один C-ID — один самостоятельный график; единые фильтры и стили. Причина: независимая работа участников и минимизация ручного BI.
- ADR-002 (исходный план, реализован; уточнён ADR-005): Vite + JS + ECharts + DuckDB-Wasm, чтение Parquet из public/data; альтернативный Supabase может потребоваться при иных требованиях к приватности/данным.
- ADR-003 (обязательно): единственные версии формул в docs/metrics.md и будущем src/shared/metrics; считать контрольные итоги из фактов, сверять с PL_Control/Cash_Control.
- ADR-004 (обязательно): ветки, PR, проверка интеграции, запрет на прямые изменения main; изменения архитектуры в отдельном PR.

## Исторические открытые вопросы до реализации MVP
- Не выбраны конкретные владельцы областей, CODEOWNERS и правила branch protection (нужны реальные usernames и администратор).
- Закрыто ADR-005: Vite, DuckDB-Wasm, ECharts, CI и Pages внедрены; новый UI-контракт описан в docs/chart-contract.md.
- Не проверены все 258 схем полей по исходным Parquet и соответствие заявленным числам строк; нужен автоматический manifest/checksums.
- **Полный исходный HTML не сохранён в репозитории.** Его необходимо добавить в `docs/reference/Инструкция.html`, иначе эта сводка не заменяет оригинальную спецификацию.
- Не утверждён способ безопасной публикации данных: сейчас синтетика, но `public/data` будет открыта пользователям Pages.
- Не решены UI-дизайн и точное расположение всех графиков: менять через макет, а не через произвольные локальные стили.

## Как вести журнал
При архитектурном изменении добавь ADR-005 и далее с датой, вариантом, почему выбран, альтернативами, влиянием на совместимость и связанным PR. Не удаляй устаревшие решения; помечай «заменено».


## ADR-005 — 2026-11-14: декларативный chart и явный admin
Заменяет ограничения и устаревшие статусы выше: Vite, DuckDB, ECharts, GridStack, CI и Pages уже реализованы. Сохраняется выбор стека и финансовая методология. Исполняемый модуль каждого графика заменён JSON-декларацией; один общий каталог SQL и renderer. Это намеренное ограничение выразительности: новый источник/тип требует admin, чтобы обычная задача не меняла оболочку. BATCH из прежнего несмерженного предложения удалён; только chart/admin.

## ADR-006 — 2026-11-14: пользовательские пространства
Боковая панель и фиксированный overview заменены компактной навигацией по пространствам из localStorage v2. Создание и переименование в UI, миграция v1, экспорт/импорт, undo/redo. Не вводится скрытая серверная синхронизация; для команды обмен JSON. Новые графики доступны в каталоге без правки общего макета.

## ADR-007 — 2026-11-14: автоматическая доставка после проверок
Заменяет требование ручного review в прежнем процессе. Агент может коммитить, открывать и сливать PR в рамках поручения без отдельного одобрения человека, после CI актуального SHA. Прямой push в main не нужен. Required checks с нулём обязательных approvals — отдельная настройка GitHub, её статус нельзя утверждать по содержимому Markdown.

## ADR-008 — 2026-11-15: карточка KPI и Sankey в едином контракте
На базе существующего JSON-контракта добавлены два явных типа: `indicator` (одно числовое поле, необязательная явно указанная агрегация) и `sankey` (два текстовых поля этапов и один неотрицательный аддитивный поток). ChartManager сохраняет единые фильтры, состояния и таблицу значений. KPI отображается текстом, Sankey — через штатную ECharts-серию с выделением источников. Произвольный JS/SQL/CSS в декларациях по-прежнему запрещён. Выбрано расширение общего рендерера вместо автономных виджетов; существующие chart.json и макеты не мигрируют. Источник реальных переходов между RFM-сегментами отдельно утверждается по схеме и методике подсчёта, данные не подменяются примером.

## Актуальные открытые вопросы
Полного исходного словаря нет, детальная финансовая сверка не реализована, большая часть C01–C24 ещё впереди. Правила GitHub требуют отдельной настройки администратором. Нет многопользовательского сохранения пространств. Изменение источников/метрик остаётся самостоятельной проверяемой задачей.
