# Архитектура и контракт приложения

## Цель
Одна самостоятельная оболочка дашборда + независимые графики, каждый в отдельном модуле. Не нужен ручной перенос и настройка каждого графика через BI-конструктор. Целевая платформа: Vite, vanilla JS (если фреймворк понадобится — отдельный ADR), ECharts, DuckDB-Wasm, Parquet из `public/data/`.

## Границы
- `src/app/`: маршрутизация/макет, навигация, порядок расположения модулей.
- `src/shared/data/`: единый экземпляр DuckDB, безопасная регистрация таблиц, очередь запросов, кеш, отмена, обработка ошибок.
- `src/shared/metrics/`: единые SQL-определения, измерения и тестовые эталоны. Никакой второй формулы ARPU в модуле графика.
- `src/shared/filters/`: единое типизированное состояние (период, тариф, привлечение, оплата, партнёр, регион, устройство).
- `src/shared/ui/`: тема, сетка, карточки, легенды, состояния загрузки, подсказки, формат RUB/%/часов, адаптивность.
- `src/charts/C01-.../`: визуализация, локальные преобразования данных и декларация поддерживаемых фильтров.

Это **целевая** структура: физические директории создавать при реализации приложения, не считать её существующей заранее.

## Контракт графика (проектное решение, закрепить типами/тестом при реализации)
Экспорт по соглашению: `id` ('C01'), `title`, `question`, `metrics`, `sources`, `grain`, `dateRole`, `supportedFilters`, `unsupportedFilters`, `load({filters,query,signal})`, `render({container,data,theme})`, `dispose()`. Может использоваться эквивалентный интерфейс, если он документирован и валидируется единым тестом.
Все графики получают фильтры из одного store, не создают собственных глобальных контролов. Реестр гарантирует уникальность ID, наличие метаданных и регистрацию на странице. Необходимы loading/error/empty состояния.

## Производительность и устойчивость
1. Держать один DuckDB-Wasm worker/инстанс на вкладку. Не поднимать базу на каждый график.
2. Регистрировать Parquet по требованию, не загружать все 32 факта при открытии. Предпочитать projection/aggregation SQL; не передавать сотни тысяч сырых строк в ECharts.
3. Реализовать централизованную очередь/ограничение параллелизма запросов, debounce фильтров, отмену устаревших запросов, кеш по ключу (таблицы+параметры+версия данных) и индикацию долгих операций.
4. Для больших фактов, особенно `viewing_daily.parquet` (~10 MB), измерить время чтения, распаковки, SQL и рендера; при необходимости подготовить **версионированные предагрегаты**. Не менять источник без проверки точности.
5. При публикации через GitHub Pages настроить корректный Vite `base` для пути репозитория, Content-Type и доступность Parquet; проверить в реальном браузере WebAssembly/worker и ошибки CORS/range requests.
6. Стратегия на будущее: если публичная раздача данных недопустима, перейти к защищённому API/агрегированным данным. Не считать приватный GitHub защитой публичных Pages.

## Семантика фильтров
- Период влияет на дату признания конкретной метрики, а не автоматически на event_date всех таблиц.
- Тарифы PL1/PL2 — прямые, PL3 — партнеры, PL4 — аренда (не подписка). Не складывать их знаменатели без определения.
- Канал привлечения — Users/Trials; канал оплаты — Billing_Events/Subscriptions/Rentals. Не путать.
- Партнёр — только сегменты со связью по partner_id. Регион/устройство — атрибуты Users или факт просмотра; не фильтровать ими общую P&L без метода распределения.
- Для каждого графика поддержка фильтра — явная декларация. UI объясняет, что недоступно. Для агрегатов без требуемого разреза выводить «недоступно», не имитировать точность.

## Проверка качества
Загрузки, фильтры, уникальные ID, схема колонок, пустой результат, NULL, двукратный JOIN, отключённый worker, кеш, повторный рендер, маленький экран, Pages base path. Финансовые тесты сравнивают помесячные агрегаты с PL_Control и Cash_Control; не ограничиваться визуальным совпадением графика.
